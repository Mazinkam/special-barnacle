# Orchestrator Efficiency and Evidence — Design

## Purpose and scope

Make the shared orchestrator cheaper in wall time and peak memory without losing the evidence needed to decide whether orchestration saves money or time at an acceptable quality level. The user asked for all fixes from the 2026-09-23 whole-system audit, in a separate worktree, using the existing `premium` orchestration profile. Success means lower measured refresh overhead, bounded diagnostic growth without irreversible loss, reliable ingestion and state publication, and an honest report of cost, duration, coverage, and verified outcomes. The current state root and its files are not migration test fixtures: use temporary copies and synthetic data.

This is one coordinated program delivered as independently testable slices: (1) telemetry/evaluation, (2) state refresh/publication, and (3) ingestion/diagnostic retention. Each slice must work with the existing JSONL stream and can be reviewed separately. No SQLite migration or automatic deletion is included.

## Existing behavior and baseline

- `bridge/extensions/orchestrator/index.ts` launches separate Python CLI processes to record events, metrics, and outcomes. `orchestrator/cli.py` rebuilds a ledger and/or regenerates a dashboard on individual writes; `orchestrator/runtime.py` loads entire JSONL files into memory. `orchestrator/state.py` serializes competing ledger rebuilds but does not synchronize event append with a final snapshot. `orchestrator/dashboard.py` directly writes HTML.
- On a temporary copy of the 2026-09-23 state, one `event` invocation took about 0.25 s and 84 MiB peak subprocess RSS; a `metric` invocation took about 0.24 s and 78 MiB. Doubling stream sizes raised these to about 0.31–0.34 s and 131 MiB. These are indicative single-run measurements, not service-level targets. Re-measure with the same fixture and commands after each slice, including a 4x stream fixture, reporting median wall time, peak RSS, subprocess count, and bytes read/written.
- The shared root was about 283 MB; completed/active run artifacts accounted for about 264 MB, largely `.events.jsonl`. A read-only baseline script reported $104.08 orchestrated cost versus a $136.57 flat-Sonnet token-profile counterfactual, but only 168/332 non-decision work records were priced. Those figures are neither a verified causal saving nor a justification for deleting unpriced data.

## Design alternatives and decision

1. **Chosen: preserve JSONL as the durable history, batch/coalesce writes, stream derived views, and optionally archive run diagnostics losslessly.** Low migration risk, maintains a simple recovery path, and targets observed cost first. Carefully specified consistency is required at batch and publication boundaries.
2. Replace all JSONL with SQLite/WAL now. Easier indexed queries and transactions once migrated, but requires a dual-runtime migration, backup/rollback, locking policy, and equivalence verification before it can be authoritative. Disk savings on the current 5.9 MB active metric stream would not solve the 264 MB run-diagnostic footprint.
3. Keep current per-record writes and only compress diagnostics. Lowest code change, but does not address process startup, full-history scans, peak RSS, ingestion duplicates, or missing evaluation coverage.

SQLite is allowed later only as a rebuildable cache/index if benchmarked historical lookup costs justify it. An index is never an independent source of truth. Switching the canonical stream to SQLite is a separate explicit design and migration decision.

## Slice 1: trustworthy evaluation and instrumentation

Define a stable run identifier shared across lead/worker events, model calls, retries, review, QA, CI/human costs where available, and terminal outcomes. Record start/finish timestamps and monotonic elapsed time for live runs; historical runs with incomplete timestamps remain `unknown`, never zero. A complete-run rollup reports wall time, known and unknown cost separately, token/cache provenance, number of workers and retries, verification result, reopened/regression outcomes when observed, and orchestration overhead (lead/scout/review/verification/rework) rather than just implementation calls. Emit explicit `unmetered` for missing cost or tokens; report priced coverage by calls and by runs, and avoid declaring savings if either cohort lacks coverage. Do not treat a model call, verification marker, and decision row as interchangeable samples.

Routing statistics join costs and outcomes by run/task and comparable task-class, complexity, risk, capability, effort, verification, and topology; interactive-session ingestion is excluded from orchestrated route statistics. Count independently verified tasks and eligible runs, not arbitrary metric rows, when applying `min_samples`. In `enforce` mode empirical topology must meet the same evidence threshold as package routing; otherwise use the deterministic topology and show the fallback reason. Keep the configured routing mode and quality gates unchanged by default. Baseline comparisons remain explicitly *counterfactual estimates* using observed tokens; only matched real cohorts with comparable verified outcomes, priced coverage, and total overhead can be described as observed evidence of savings. Report latency and cost together, with sample sizes and missing-data flags.

Tests cover missing price/token/duration, separate call and verification rows, duplicated rows, cross-cohort joins, session-ingest exclusion, one-sample topology under `enforce`, and delayed outcomes. Preserve existing cost sources and attribution and avoid fabricating historical data.

## Slice 2: lower refresh cost with durable visibility

Add one small batch-write interface at the Python CLI boundary for an ordered set of validated event, metric, and outcome records. The HT bridge batches related dispatch writes and refreshes once per batch or run boundary rather than starting Python per record; expose a bounded batch size and drain outstanding writes on run completion, cancellation, crash, and shutdown. A failed batch must return an error to the bridge; no silent drop or duplicate retry. Maintain existing single-record CLI commands for other runtimes. Do not postpone user-visible progress or terminal status merely to improve benchmarks. Batch size and refresh cadence must not weaken event durability: append/flush the canonical records before acknowledging success and regenerate the dashboard for each successful batch invocation.

Use one process-safe writer coordination rule for check/append/rebuild and a durable ledger checkpoint/stream offset or equivalent to avoid replaying all events for each refresh. A published ledger must represent a complete event prefix; concurrent appenders must not leave a schema-valid ledger permanently behind acknowledged work. Replays must remain possible from original JSONL after interrupted writes, checkpoint corruption, or schema upgrades. Serialize snapshot writes without turning independent readers into long-blocked writers. Publish dashboard HTML by same-directory temporary-file atomic replace. An interrupted render leaves the previous valid page in place; a later refresh catches up. Return/emit clear refresh failure status even if a durable record was already appended, so a retry cannot blindly append duplicates. All mutations are idempotent by stable record identifier, including retries after an ambiguous subprocess exit.

Reduce *peak transient memory* by streaming complete-history reductions, bounded deques for recent display rows, reusing loaded/streamed outcomes in aggregates, and removing redundant sorts/scans without dropping full-history totals. Do not truncate the canonical event or metric streams. Tests use spawned concurrent processes, interrupted writes, a torn/trailing partial JSONL record, duplicate batch retry, a failed dashboard render, and 1x/2x/4x comparison fixtures. Existing `load_or_rebuild` and dashboards must work through a rolling upgrade with legacy JSONL; no mandatory live-state migration.

## Slice 3: efficient, concurrency-safe ingestion and lossless diagnostics

Ingestion must not scan the entire session and full historical metrics on every unchanged settled turn. First benchmark repeated ingestion against realistic copied session files; implement a persistent per-source checkpoint (offset and identity/fingerprint or equivalent) only where it improves measured work. Incremental ingestion must recover from session truncation/rotation, incomplete last lines, crashes between checkpoint and append, and repeated imports without omissions or duplicate costs. Coordinate deduplication and append across processes under the same authoritative writer rule; share one metrics pass where a historical scan remains necessary. Switching between session-level and per-call granularity must explicitly prevent double counting, or reject the switch with an actionable diagnostic until reconciled. Existing event/metric provenance stays intact.

Keep active and recent completed run files human-readable. Provide a dry-run archive command that enumerates eligible **completed** run diagnostic files, original and estimated compressed bytes, and exact destination paths. A separately confirmed execute mode losslessly compresses older completed diagnostics into the same shared root, verifies hashes/decompression before replacing raw diagnostic copies, and provides a documented restore/read command. Default behavior performs no deletion; compressed archives remain locally recoverable indefinitely. Never archive an active run; never archive or prune authoritative `events.jsonl`, `metrics.jsonl`, `outcomes.jsonl`, or their integrity/recovery metadata. If a run is incomplete, age and status are ambiguous, or verification fails, skip it with a reason. Do not silently break links shown in the HT progress board; recent `run.log` remains readable, archived paths have a clear lookup/restore message. No automatic deletion or irreversible retention timer is introduced.

Tests cover dry-run with no writes, active/incomplete runs, archive/restore byte equality, interrupted archive, repeated archive, low disk space, log path discoverability, concurrency with a writer, and ingest rotation/retry/granularity transitions. An archive is not counted as freeing audit evidence; storage accounting distinguishes raw from compressed bytes.

## Shared interface, rollout, and verification

Keep one event-sourced state root across coding-agent runtimes and keep the existing `EventStore`/CLI operations backward-compatible. The new batch/checkpoint/index machinery belongs behind a small durable-store module interface; HT bridge calls it, but does not reimplement its transaction or reconciliation rules. Keep persisted format/version explicit and documented. New derived files are rebuildable from JSONL; use standard-library facilities unless a measured need justifies a dependency. Set `CODING_AGENT_RUNTIME` and canonical `CODING_AGENT_REPOSITORY` on writes. A copied live fixture is used for reproducible perf and migration tests; do not run benchmark appends or archival on the real root.

Verification gates: unit and cross-process integration tests; full Python and bridge test/typecheck commands where available; before/after subprocess count, median wall-time and peak-RSS measurements; byte-for-byte comparison of canonical JSONL and equivalent ledger/dashboard aggregates on copied inputs; priced/unpriced and duration coverage; quality-gate/routing-mode parity; dry-run archive/restore. If an optimization changes observed outcomes or loses records, revert that slice rather than accepting the speedup. Worktree tests and commands must set the skill-root override so HT does not accidentally import the installed main checkout. Use the defined `premium` profile for any orchestrated implementation/review, subject to existing risk and reviewer-independence rules; `premium` does not authorize changing safety policy or increasing fanout without evidence.

The worktree is not a live deployment: the shared skill symlink still points at the main checkout. After review and integration, Python CLI spawns load new code on their next invocation; a running HT extension that contains modified TypeScript may require an HT extension reload/restart. Document the exact reload and recovery steps; do not claim an unmerged worktree is already installed.

## Out of scope and unresolved risks

No destructive cleanup of existing 264 MB of run artifacts, no automatic routing-enforcement promotion, no unverified claim of monetary savings, no change to model pricing tables, no SQLite-as-source-of-truth migration, and no deletion of live state. SQLite indexing, long-term external archives, and actual causal model comparisons require their own measured proposals. Advisory locks and atomic replacements need the same macOS/Linux coverage as current code. Excessively frequent batches could erase startup savings; excessively delayed batches could make status stale, so use measured defaults and a forced terminal flush. Cross-process event append, batch retries, and dashboard publication are correctness risks and receive regression tests before optimization code.
